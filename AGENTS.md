# AGENTS.md

Dash for Cloudflare is a native iPhone Cloudflare client. The installed name is `Dash`, the bundle identifier is `sh.xat.dash.app`, and OAuth returns through `dash://oauth/callback` after the stateless HTTPS relay.

## Product scope (UI)

- **iPhone only.** The Xcode target is `TARGETED_DEVICE_FAMILY = 1`. Design, implement, and polish for portrait iPhone. Do not design, implement, polish, or “fix” iPad / iPadOS / Stage Manager / Split View layouts unless the user explicitly asks.
- **One compact canvas per tab.** Navigation is workspace layers on a single phone stack — not `NavigationSplitView`, not sidebar + detail, not dual adaptive layouts. Prefer the compact path for all new work.
- **Do not reintroduce regular-width layout forks.** No `horizontalSizeClass == .regular` chrome, no split selection APIs, no reading-width content columns for “iPad readiness.” Optimize for iPhone; ignore iPad parity.

## Workspace

| Path | Purpose |
| --- | --- |
| `apps/ios` | Swift 6, SwiftUI, Observation, iOS 17+ app and tests |
| `packages/cloudflare-api` | Platform-neutral Swift Package for OAuth and Cloudflare APIs |
| `apps/web` | Vite + React landing page and Hono edge app at `dash.xat.sh` (worker `dash-relay`); hosts the OAuth callback and the RDAP/WHOIS registration snapshot |
| `packages/ui` | Web-only component library; do not import it into Dash |

## Commands

```sh
pnpm install
pnpm ios:build      # signed simulator build
pnpm ios:device     # signed device build
pnpm ios:test       # unit + UI tests on an iPhone 17 Pro simulator (Xcode 26+)
pnpm api:test       # Swift Package tests, no simulator needed
pnpm typecheck      # turbo typecheck + api:test + full simulator build (slow)
pnpm lint
pnpm lint:fix
pnpm lint:l10n      # literal DashL10n / Text keys must exist in Localizable.xcstrings (part of lint)
pnpm ios:icons      # regenerate Solar chrome + Hugeicons file-format assets
pnpm web:dev        # landing + edge worker locally
pnpm web:deploy     # versions upload → deploy dash-relay (landing + OAuth relay)
```

Single tests:

```sh
swift test --package-path packages/cloudflare-api --filter <testFunctionName>
xcodebuild -project apps/ios/Dash.xcodeproj -scheme Dash \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -allowProvisioningUpdates -only-testing:DashTests test
```

All iOS build and test commands use Automatic signing with team `UH4FQTHMG2` (`apps/ios/Config/Signing.xcconfig`). OAuth secrets stay in ignored `Config/Secrets.xcconfig`.

Before finishing a task, run `pnpm lint:fix` and `pnpm lint`. Do NOT run simulator builds or tests (`pnpm ios:build`, `pnpm ios:test`, `pnpm typecheck`) unless explicitly asked — they take too long; the user batch-verifies everything themselves later. `pnpm api:test` is seconds-fast and fine when `packages/cloudflare-api` changed. Commit frequently using Conventional Commits, but note Lefthook's pre-commit hook runs `lint:fix` and `typecheck` on staged changes, so a commit itself triggers a simulator build — ask before committing when that wait matters.

## Architecture

### iOS app

- One `AppModel` (`@Observable @MainActor`, created in `DashApp`, injected via `.environment`) owns the `CloudflareClient`, `KeychainTokenStore`, `FeatureDataCache`, auth state, accounts, and active-account selection. Switching accounts or signing out clears the cache.
- `AppRootView` switches on auth state into `MainTabView` with three primary tabs (Home, Resources, Watchtower), each with its own `DestinationNavigator` page-instance store rendered by `DestinationStackHost` through Dash's plain UIKit containment controller — **not** `NavigationStack` or `UINavigationController`. Resources stays a browse-only catalog. Every drill-down routes through the `Destination` enum (`Catalog.swift`) into `DestinationRoutedContent`; a new screen means a new `Destination` case plus an exhaustive branch there. Back / Close are explicit page-chrome actions, VoiceOver Escape mirrors them, and there is no edge-back gesture. The page compositor speaks exactly three languages and `DashPageTransitionRules.role` is the only place that picks between them: **flow** is the horizontal handoff every drill-down uses — Resources into a feature, a feature into a resource, a resource into its settings — deliberately the same step a tab change makes, so a push and a swipe read as one motion; **card** is the Family expansion, and it is a property of the *source*, not the destination — only a tap that hands over a `DashNavigationHero` earns it, which today means one place, the Domains card grid opening zone detail (the same zone reached from a Home row or a recent is a plain flow drill). The card's **enter is slightly underdamped** (`cardEnterDampingRatio`, tuned by eye between 0.72-stiff and 0.62-rubbery) so the hero overgrows its seat by a few points and settles — and that bounce only exists because the morph timeline rides an **unclamped position spring** on the invisible driver, not opacity: a layer's presentation opacity clamps at 1, which flattens any overshoot into a dead stop, which is why `cardDampingRatio = 1` used to be the only honest value. Progress past 1 reaches exactly one consumer — `DashCardMorphRules.heroFrame`, floor-clamped only — while every opacity curve clamps internally, and the pop reads a clamped copy because a collapse extrapolating into the grid it returns to is not a bounce, it is a dip (`cardExitDampingRatio = 1`). A card flight also **paces itself to the ground it covers** (`DashCardMorphRules.flightDuration`): one fixed duration makes speed proportional to distance, so a bottom-row card lunged where a top-row card glided — flights past `referenceTravel` stretch linearly up to `maxFlightStretch` at `farTravel`, pops included, and Reduce Motion bypasses the rule with the rest of the proxy path; **workspace** is Settings' vertical train, the one route with Close instead of Back — a plain crossfade in a fixed header slot, deliberately with NO avatar flight onto a landing seat in the arriving page (that morph existed, was never reachable because the seat was never published, and is now removed; `dashNavigationLanding` serves the card morph alone). There is no fourth "entity" expansion that grew a captured row snapshot into a page — every non-card drill-down used to take it, and beside the real card morph it read as a second, weaker morph. A card morph whose two seats are not both usable falls back to flow, never to a bespoke failure pose. **A source occurrence's claim flag is per anchor** (`DashNavigationAnchorClaim`, one `@Observable` box each, registered with the registry on appear and re-armed from its plain `claimedInstanceIDs` set so an occurrence remounting mid-flight does not come back visible and double the element). It was ONE shared `@Observable` `Set<UUID>` that every anchor's body read, and `@Observable` tracks per PROPERTY: claiming one source invalidated every anchor in the app — sixty Domains cards, every Home row — four times per card morph (claim×2 on the frame it starts, release×2 on the frame it lands), which is a whole-app relayout landing exactly where the morph needs its frame budget. Anchors also no longer publish a `DashNavigationAnchorFramesKey` preference: a dictionary-valued BOUND preference recomputed by every contributor in that same storm is what logged "tried to update multiple times per frame", and it was the third and least accurate of three frame stores — preferences cannot cross a `UIHostingController` and every route is one, so it could only ever describe outer chrome the live probe and `hostedFrames` already cover.
- Root header invariant (`dashCatalogScreen` + `MainTabView`): the header is ONE component for the whole app — `DashWorkspaceHeaderBar` (`DashWorkspaceHeader.swift`), floated by `MainTabView` above the pager exactly like the wash, with three slots: a leading control, a centred title, trailing controls. A page never draws them. Every tab root and destination is still wrapped by `DashRoutePageChromeHost`, which still reserves the same fixed header height inside the page — the reservation is the invariant that keeps the content rest line still, and only the *painting* moved out. Pages keep declaring `detailHeader` / `dashPageActions`; those preferences cannot cross a `UIHostingController`, and every route is one, so `DashRoutePageChromeHost` publishes the resolved descriptor into its navigator's `DashPageChromeStore` under the page's entry id and the bar reads it there. Like `DashHeaderScrollState` and `DashWorkspaceWashScroll` that store has exactly ONE reader — never read page chrome from `MainTabView`'s body, or an in-page action change (an R2 selection, a Save becoming enabled) refreshes every cached page host mid-transition. Chrome is published only when the page's preference actually resolves — NEVER from an `initial:` publish: the first body evaluation runs before preferences have propagated, so an initial publish speaks with the default-empty voice, blanks the shared title on the very frame a push lands, and turns every title change into remove → gap → insert (the holdover below depends on "has not spoken" being observable). It is also never withdrawn on disappear — the container detaches a covered page's view — so `DestinationNavigator.replaceEntries` prunes the store instead, and chrome lives exactly as long as its entry. **The bar renders a `displayed` mirror of the resolved state, written ONLY inside an explicit `withAnimation` at the write site.** This is not a style choice: `MainTabView`'s `.dashTray` hosts end with `.transaction { $0.disablesAnimations = true }` (`DashChrome.swift`, both tray modifiers), and those wrap the whole `tabContainer` — every modifier-attached animation (`.animation(_:value:)`, transition-only mounts) is force-disabled for ANY chrome living in `MainTabView`'s own tree above the pager. The page-local bars and the header frost never noticed because they live inside route `UIHostingController`s, and a hosting-controller boundary stops transaction propagation; the shared header does not have that shelter. Explicit write-site `withAnimation` into view-owned state is the one mechanism that survives the rewriter — the same one the tray reveal and toast dismiss already use. Do not "simplify" the mirror back to `.animation(_:value:)`; it will silently never fire. A page difference is therefore a change of slot *content*, resolved by `DashWorkspaceHeaderRules.state`. **The header speaks the compositor's three languages, and gets the role from the very same `DashPageTransitionRules.role`** — `DashNavigationMutation` carries the entry the mutation is about (arriving on a push, leaving on every dismissal) precisely so the bar cannot disagree with the page about which step is happening, and `DashPageTransitionRules.duration` / `.dampingRatio` are ONE pace table both halves read, so the bar settles on the page's own timeline instead of a generic spring (the workspace train exits in 0.22s; a Close still easing out after it reads as chrome that never belonged to that page). **Header slots do NOT travel** (`DashWorkspaceHeaderRules.travel` is always zero): leading morphs in place, the title swaps instantly, and a leftover Settings Y-ride was sliding the Watchtower inbox whenever that tab's `lastMutation` was still workspace. Role still decides the **pace** — a card's slower 0.38s, not flow's 0.3s. **The title swaps instantly, by decision** (2026-08-06): it briefly carried a two-part morph — keyed glyph dissolve beside a `contentTransition` text swap — and the animated blur ran per-frame main-thread work in the same window where the page compositor's display link re-lays-out a live hero, which dropped frames. `titleSlot` now opts its whole subtree out of the seats' animated write (`.transition(.identity)` + a stripped transaction — that transaction is the one hook to remove if the morph ever returns on a better frame budget); the seats keep their animations, which are render-server work. **An arriving page still holds the standing title until it publishes its own** (`holdoverTitle` — the deepest entry that HAS published, walked statelessly, never a `@State` mirror that can fall out of step with the stack): without the hold, a drill blanks the slot for the frame(s) before the new page's preferences resolve, which reads as a flash. `chrome == nil` means "has not spoken", NOT "has no title" — a screen that genuinely wants none publishes a header-less preference, which clears the slot for real. Actions never hold over: the previous page's Delete must not sit over the page that replaced it. `dash.navigation.title` stays on the `Text`, never on a container, because UI tests resolve it through `staticTexts`. Controls cross-fade rather than blur: the blur dissolve is the title's language, and a glass circle mid-shape-morph does not want a second filter on top of it. Distance is the shorter `headerTitleStepSlide`: the bar states the direction, it does not restate the page's distance. Within that, the leading seat is ONE Liquid Glass identity (`workspaceHeaderGlassID(.leading)`) and it must NOT slide on any role — avatar, Back, Close and a page's own leading action trade that exact spot, so the seat morphs in place instead of fighting its own shape transition (a Close that rode the vertical train up with Settings read as a second, competing arrival from below). The leading `.id` keys the *visual* occupant only (Back vs Close vs avatar), never the page entry: Back → Back on a card expand or plain drill keeps one circle, otherwise two identical chevrons glass-morphed against each other. Every occupant crossfades in that one seat, the avatar included — it used to leave instantly instead, because the workspace present flew a live copy of it onto a Settings landing seat and a component must not duplicate itself mid-flight; that flight is gone and so is the exception. **Every occupant of a seat must lay out at the same `AvatarHeaderMetrics.barSize`.** `HeaderProfileButton` and `HeaderInboxButton` pull their Liquid Glass ring in with a `.padding(-7)`, which shrinks the layout box to 30pt while the circle still draws at 44 — leading-aligned against a 44pt Back that puts the two circles 7pt apart. Both therefore lock the slot back with an outer `barSize` frame (the inbox always did; the avatar did not, which is why it looked misplaced the moment the two started sharing a seat instead of living in separate layers), and `check-ios-ui-architecture` counts the two frames because a check that merely looks for the token is satisfied by the inner one and can never fail. Tab roots deliberately keep an EMPTY title slot: a drill-down is the moment a title exists at all. A push no longer displaces the header (`shouldDisplaceWorkspaceHeader` is trays only — the dock is the surface that still leaves); its slots change instead, which is the whole point. Do not seat the avatar, a title, or a back control inside a page host. The one exception is `DashPageChromeHosting.page`: a stack hosted outside `MainTabView` (previews, the UI-test harness in `DashApp`) keeps drawing its own `DashPageNavigationBar`, so it never loses Back — `MainTabView`'s three navigators are the only ones constructed with `.workspace`. The warm top wash is shared chrome of the same kind: ONE `DashWorkspaceTopWash`, painted by `MainTabView` behind the pager over the workspace canvas, so Home / Resources / Watchtower all show the same light field and the glow holds still while pages slide across it. Horizontally only: vertically the glow belongs to the top of the *content*, so it rides the active root's scroll 1:1 (`DashWorkspaceWashRules.lift`, clamped at 0 so a rubber-band pull can't drag it below its own edge, and at its 300pt depth) and leaves with the page while the frost stays pinned — pin both and the two read as one stuck slab. The distance comes from the same `DashHeaderScrollProbe` that arms the frost, through a `DashWorkspaceWashScroll` store that `MainTabView` hands to the ACTIVE page only (`dashWorkspaceWashScroll`) and `DestinationStackHost` clears again for pushed destinations: an off-screen root would fight over the one store, and a detail would drag the light behind the transparent root still sliding away. Like `DashHeaderScrollState`, that store is read by the wash view and nothing else — `MainTabView` only passes the reference, because a per-frame read in that body would refresh every cached page host during an explicit transition. That works only because tab roots are transparent — `dashCatalogScreen` paints no background of its own and `DashScrollViewConfigurator(fill: .clear)` punches the UIKit plates above the content controller (hosting wrappers, custom page-container view, page cell) through in both appearances (`DashCanvasPlateRules`). Never hand a tab root or `DestinationStackHost` an opaque plate again, and never copy the wash into a page — three washes ride their pages on a swipe and read as a seam. Pushed screens stay opaque (`dashDetailCanvasChrome` + full-bleed canvas), which is what hides the wash under a detail. The header frost (`dashHeaderScrim`, installed by both chrome modifiers, so every root and every pushed screen has one) is the exception to all of that: it is the one top layer that must live **inside** the page. `DashRoutePageChromeHost` layers custom navigation chrome above the hosted content, so a band placed in the page passes under the title and controls and leaves them crisp; float it over the pager next to the avatar and it covers them. To reach the status bar from in there it draws above its own layout box and `DashScreenClipLift` unclips the SwiftUI hosting wrappers up to — never past — the screen's own view controller (unclipping the custom page/pager containers lets one screen's chrome spill over an incoming transition). The frost imports `VariableBlur` directly through Swift Package Manager and uses its `VariableBlurView` only as the page-local backdrop; do not wrap Dash screens in `ProgressiveBlurHeader.StickyBlurHeader`, because that component owns another `ScrollView` and would break the existing screen/probe architecture. Match the reference look with `maxBlurRadius = 5`, a 40pt tail, and an adaptive white/black tint ramp at 0.7 on top, 0.5 at 56pt, and zero at the bottom. `VariableBlur` reaches the backdrop through an obfuscated private `CAFilter`; the product deliberately accepts that OS/App Store risk and tracks the package's `main` branch, so keep the dependency, resolved revision, Settings credit, and this warning together. Reduce Transparency replaces the effect with a canvas ramp whose full navigation region is opaque. The frost is **not** scrubbed by scroll position: `DashHeaderScrimRules.isScrolled` is a two-threshold flip (arm past `enter`, disarm under `exit`, hysteresis between so a resting finger can't chatter it). Crossing the threshold mounts the band with an interruptible 0.36s opacity + 8pt downward entrance that hides the filter's first composited frame; returning to the top uses the same 0.36s curve while lifting it out by 3pt, and Reduce Motion keeps opacity only. A screen's scroll view is usually not laid out when its chrome mounts, so `DashHeaderScrollProbe` re-resolves across `DashHeaderScrollProbeSchedule` — `layoutSubviews` alone fires too early and may never fire again, which leaves that screen permanently unfrosted. The probe is KVO on the screen's own scroll view writing into a per-screen `@Observable` `DashHeaderScrollState` that only the band reads; a scroll-driven value the screen body reads would refresh the page host on every frame while the explicit transition is settling.
- A **geometry action's state belongs to a leaf**, never to a view that also hosts a preference reader. `SplashOverlay` (`DashApp.swift`) owns the `lockupSize` its `onGeometryChange` writes; it used to be `@State` on `RootWithSplash`, whose body is `AppRootView().overlayPreferenceValue(DashLoginIconAnchorKey…)` — so every measurement re-ran the whole app tree AND re-resolved the landing anchor, which moved the very lockup being measured, and SwiftUI reported the re-entry as "Geometry action is cycling between duplicate values" on every cold launch. Same rule as `DashWorkspaceWashScroll` and `DashHeaderScrollState`: a geometry value gets exactly one reader, and that reader is never the body that hosts everything else.
- `FeatureID` (`Catalog.swift`) is the feature registry: title, subtitle, SF Symbol, Solar fill/outline assets, and category per feature. Every feature (zones, emailRouting, workers, pages, r2, kv, tunnels) is rich, with dedicated views in `FeatureViews.swift`, `RegistrarViews.swift`, `EmailRoutingViews.swift`, `StorageViews.swift`, `R2ObjectViews.swift`, `PagesViews.swift`, and `TunnelViews.swift`; the feature router is an exhaustive switch with no `default:`, so a new `FeatureID` must name its screen or it does not build. `GenericFeatureView` is gone. A new feature also owes `FeatureVisualIdentity.tone(for:)` a tone no sibling uses and either `DashAuthorizationScopes.coreFeatures` or `experimentalFeatures` membership — tests fail otherwise. **Tunnels is the one experimental feature**: off by default (`dash.experimental.tunnels_enabled`), hidden from Resources / Home shortcuts until Settings → Experimental opts it in, absent from `core` sign-in scopes, and authorized on demand via Grant access, which appends `argotunnel.read` + `access.read`. Email Routing browses from Resources as a domains index (`EmailRoutingDomainsView`) that pushes the existing per-zone `EmailRoutingView`; Destination Addresses stay nested under that screen. That screen is routes and settings only — the processed-messages card and Email volume chart are gone along with the `emailRoutingAdaptiveGroups` call behind them (`ResourceAnalytics.swift` with it), the same trim the R2 / KV operations charts got. The zone tool and DNS guard remain.
- Registrar is **not** a catalog feature and has no account-wide index. It was a Profile → Account row, then a Resources row ("Registrations"); both were wrong for the same reason — a registration is not something the user browses for, it is one card's worth of facts about a domain already on screen, and every name Dash can show one for is already a row under Domains. The only door is the zone screen's Registration card: when `RegistrarZoneRegistration.firstParty` matches the zone's own name in the account's registrar index, the card's header action pushes `.registrarDomain` (`dash://registrar/<domain>`) — `RegistrarDomainDetailView`, which keeps its own `FeatureWriteAccessNotice`. A domain registered elsewhere renders RDAP with no action, because it has no `/registrar/registrations` record to open. That leaves no `FeatureID` behind the screen, so three things are hand-written rather than derived: `RegistrarAccess.read` / `.write` are scope literals (`registrar-domains.read`, and `.admin` — `registrar-domains.write` does not exist), `readScopes` / `writeScopes` name `.registrarDomain` explicitly while `featureID(for:)` returns nil for it (mapping it to `.zones` would hand it `zone.write` and withhold the scopes it needs), and `detailHeader` passes `FeatureVisualTone.teal.vivid` because there is no `featureIdentity` to resolve a tint from. Both scopes ship with sign-in, in `DashAuthorizationScopes.coreReadOperations` / `coreWriteOperations` rather than on a capability: `registrar-domains.read` because the lookup runs on every zone visit and has no row to unlock, so a scope requested on demand would never be requested at all and the card would sit on RDAP forever; `registrar-domains.admin` because auto-renew and the transfer lock are what the screen exists to change, and it is reached by tapping one icon on a domain the user already opened. The screen keeps its `FeatureWriteAccessNotice` for grants that predate this. Email Routing still uses the capability pattern (`email-routing-rule.write` + `email-routing-address.write` on the capability, `FeatureReadOnlyBanner` suppressed on its domains index via `FeatureID.showsCatalogReadOnlyBanner`). Status codes go through `rdapStatusLabel`, which matches `RegistryStatusVocabulary` on a code's **letters alone**: the same EPP status arrives spaced from RDAP, camelCase from the WHOIS backstop, and lowercased-run-together from the Registrar API, and a shape-only splitter cannot break that third form — it shipped `Clienttransferprohibited`, a key no catalog can hold, so the row stayed English on a Chinese screen. Never re-derive a status label from its shape; add the code to the table.
- `FeatureDataCache` is an in-memory, session-scoped cache keyed by `FeatureCacheKey` strings, backed by an optional on-disk mirror. `AppModel` installs a real `FeatureCachePersistence` (per-account JSON files in Application Support, debounced flush) so a relaunch can repaint from the last-known data without a network round-trip and an offline launch can show it. Persistence is strictly opt-in: the default `FeatureDataCache()` (tests, previews) is pure memory. Values are persisted only when their runtime type is actually `Codable` (type-erased `encodeIfCodable`/`decodeIfCodable`); non-Codable snapshots like `WatchtowerSnapshot` or `CursorPageSnapshot` are silently skipped. Writes are account-scoped: `setPersistenceAccount` (fired from `activeAccountID`'s `didSet`) loads the active account's file into a sync mirror, so switching accounts never touches another account's data; `clear()` wipes memory only (account switch keeps disk), while sign-out and demo transitions call `clearAllPersistence()` to delete every account's file. Views read the cache in `.task` and bypass it from `refreshable` with `force: true`. A cold screen with no fresh data but a stale copy on disk seeds it via `getStale` and refreshes in place, so the failure banner lands over last-known data instead of a skeleton.
- Loading contract (`DashListPhase` via `DashFeatureList`): one `@ViewBuilder` body receives `DashBodyMode` (`.placeholder` / `.live`) so cold and live share structure — never a parallel skeleton tree. **Cold** (no cached primary payload) → body in `.placeholder` (redacted / geometric stand-ins, non-interactive) — never an empty shell plus “Updating…”. Catalog lists use `dashModeListRows` (default depth `DashBodyPlaceholderDepth.listRows`); Domains uses the same card grid with `domainCards` placeholders; details over-reserve the fuller first-paint stack (panels, info groups, toggles, chart cards — `DashListRowPlaceholder`, `DashMetricPanelPlaceholder`, `DashCollapsedChartPlaceholder`, Watchtower’s saved-layout metric cards). The first cold → live handoff animates with `DashBodyTransition` (surplus placeholders recede (scale 0.97 + blur + fade), extra live slots insert; index-aligned slots replace in place). **Warm** (content already shown) → keep `.live` and the inline “Updating…” strip — refresh never remounts placeholder. **Empty settled** → the same placeholder body stays mounted and empty copy lands on the cold wash (`DashFeatureEmpty` via `dashColdOverlay` — same mount as failure); never swap in a bare `DashEmptyState` that tears the bars down. Nested empties inside an already-loaded detail and product-off CTAs may still use `DashEmptyState` in content. Secondary fetches inside a loaded detail (build log, traffic, preview) may use a local ring + short copy (section cold). Do not invent a fifth full-screen spinner.
- Read-only label/value blocks on pushed screens are `DashInfoGroup` + `DashInfoRow` (`DashSurfaces.swift`) — the same two-tone frame as Home's Shortcuts and Recently used, title on the header band, rows in the card below. Do not hand-roll another `DashCard` with a `footnoteSemibold` heading inside it. A group that fetches on its own carries a `DashSectionPhase`: **loading** paints placeholder rows the arriving values land on (a section that pops in later is a layout shift, not a load), **content** shows the rows, **failed** veils the message and a Try again over those same placeholders (`DashSectionFailureVeil` — the section-scale `dashColdFailure`, compact because that one's 72pt mark is sized for a screenful of skeleton). Empty and failed are different answers: a lookup that legitimately returns nothing may drop its section, a lookup that threw never may — conflating them in one optional is how the zone registration card failed silently. Info groups are bounded; like `DashListGroup` they own an eager stack, so never put an unbounded `ForEach` in one.
- Two frames, one rule, so a titled block of section content has exactly one right answer: **a chart or a metric is a `DashGlassCard` with its own `footnoteSemibold` heading inside; read-only label/value fields are a `DashInfoGroup`** on the two-tone band. Charts never move onto the band — Watchtower's reorderable metric cards could not follow, so the analytics screens would end up split across two frames. Pages build outcomes, DNS record types, and the WAF summary + country globe were `DashCard` outliers and are now glass with the rest. **A donut is a filter, not a metric with a history**: neither pie carries a `DashChartDetailButton`, and `DashChartDetailContent` holds time series only — the legend already names every slice and the filter strip already states the count, so a pushed copy would restate the card and hand back a second, unfiltered selection. That legend is the pie's only labelling, which is why `DashSystemPieChart` draws its own instead of `.chartLegend(.automatic)`: a `SectorMark` styled by a resolved color rather than `by:` emits no Swift Charts legend at all, so Settings → Chart style = Swift Charts shipped the filter with nothing to read or tap. It mirrors `DitherLegend` — chips toggle, the unselected dim, a selection that stops naming a slice clears itself so Load more can widen the data — except that sector taps only ever select, because `chartAngleSelection` keeps writing while a finger crosses the donut and a toggle there would flicker the filter under one gesture. `DashCollapsedChartCard` is the same enamel in its collapsed pose — one reserved title line (two once it carries a total) over a plot flush to the bottom edge, half a row wide, the whole surface pushing the detail; a `DashChartDetailButton` chevron belongs to expanded cards, because beside a target that is already the card it is furniture — so it composes its own panel instead of nesting in `DashGlassCard`, whose uniform padding cannot let a plot reach that edge. Two of them replaced the Worker screen's `DashTextTabs` chart switcher: the totals now own one panel and each chart is its own card, and a collapsed card never repeats a total the panel above it already shows. The WAF screen shipped exactly that duplicate — a `DashGlassCard` stating the blocked total over a collapsed card stating the same total under the same words, and that card had no `detail` to push, so the second copy bought nothing. **One metric is one card**: the collapsed card carries the total, and a card that stands alone names its own window through `caption` (paired half-width cards leave it nil — one captioned card beside an uncaptioned one breaks their shared height) instead of borrowing a panel that must then repeat the figure. The plain metric tile survives only as the no-history pose, where there is nothing to plot. **A breakdown of a metric is not a second metric**: `DashChartDetail.countryBreakdown` carries the blocked-by-country globe into the push, so the screen shows the metric once and the map that says where those events came from sits behind the same tap. A breakdown **replaces** `DashChartDetailView`'s exact-value table rather than stacking above it — that table only transcribes the plot, one row per point, so it earns the page when the page has nothing else to say about the data; where the events came from is the second reading of the same series, and the transcript under it would be furniture. Details with no breakdown (Web Analytics, Workers, Zone Analytics, Watchtower) keep the table. `DashChartCountryBreakdownSection` owns its camera and selection so the pushed detail and the WAF screen's no-history fallback (no series, hence no detail to carry it) mount the same section, and it caps and ranks its own buckets so the markers and the ranking under them cannot disagree about who leads. Web Analytics is the same card in a two-column grid — Visits and Page views, one row, accessibility sizes reflowing to one per row. **Core Web Vitals are not on that screen and the client does not fetch them**: LCP, INP and CLS share no unit, so the grouped bar chart that held them had to express each column as a share of its own poor threshold — a second scale the card then had to teach before either reading meant anything, for three numbers Cloudflare only publishes as p75 quantiles (never the good / needs-improvement / poor distribution the bands imply). Page-load time went the same way earlier. ### Auth flow

- `AppModel.signIn()` builds a PKCE authorize URL and opens `ASWebAuthenticationSession`; Cloudflare redirects to the relay's HTTPS callback, which 302s to `dash://oauth/callback`; the app exchanges the code and stores tokens through `KeychainTokenStore` (an actor implementing the package's `TokenStore` protocol).
- Fresh real-account sign-in requests `DashAuthorizationScopes.core`, the audited union of every permission used by current features, in one consent flow. Any later OAuth reauthorization also requests `core`. `initialReadOnly` remains the Demo profile; App Intents and the share extension fail closed without write scopes and ask the user to connect a real account. Lower-layer write checks still enforce mutations.
- Configuration plumbing: `Config/Base.xcconfig` `#include?`s the ignored `Signing.xcconfig` and `Secrets.xcconfig`; `DASH_CLIENT_ID`/`DASH_REDIRECT_URI` flow into Info.plist keys read by `AppConfiguration.current`. Unexpanded `$(...)` values mean unconfigured, which disables sign-in with a hint instead of crashing.

## Swift conventions

- Use Swift 6 strict concurrency, `async throws`, actors for shared mutable state, and `@Observable @MainActor` for UI state.
- Prefer SwiftUI system navigation, lists, searchable, refreshable, sheets, semantic colors, SF Symbols, and Dynamic Type.
- Phone-first: do not add iPad adaptive layouts, regular-width split navigation, or size-class layout forks (see Product scope above).
- The shared palette is defined in `DashTheme`; do not scatter literal colors through feature views.
- Press feedback: the 0.97 shrink (`DashPressButtonStyle`) is reserved for genuine **button** controls — pills, circular icon buttons, toolbar/back/close actions, small text actions (Cancel, Back, Save, Show more…), and tab labels. Tappable **surfaces** — full-width rows, list items, cards, and tiles — must NOT shrink: give them `DashSurfaceButtonStyle` (no scale, no press animation). `DestinationLink`/`DashListGroupLink` navigation rows already use the surface style. When a tap target reads as a row/card/tile, it is a surface, not a button. Sanctioned exception: the Home Quick-actions tool tiles (`DashToolTile`) are launcher buttons and take `DashPressButtonStyle` — the shrink plus haptic is their press cue, and the tap still opens the action's tray.
- Held gestures: any surface that reads a finger continuously — every chart (`DitherHoldInteraction`) and the globe (`GlobeHoldInteraction`) — arms on a 0.35s hold inside 10pt, announces it with `DashDelight.gestureEngaged()`, and then owns the touch until it lifts: on arming it switches off every ancestor pan/swipe recognizer (list scroll, tab pager, interactive pop) and restores them on release, teardown included. Both packages carry the same two constants and the same claim rule; change one and change the other. Do NOT give such a surface a `DragGesture(minimumDistance: 0)` or an immediately-recognizing pan — that reads the finger before the user has committed and fights all three page gestures at once. A plain tap still lands immediately; only the continuous read waits for the hold.
- App code depends on `CloudflareAPI`, never on JavaScript packages or `packages/ui`.
- Tokens belong in the Keychain. Local OAuth values belong in ignored `Config/Secrets.xcconfig`; never commit credentials.
- Preserve graceful 403 handling. A missing OAuth scope must affect only its feature and should surface an actionable error.
- Use the exact Cloudflare OAuth scope IDs in `CloudflareScopes`. Write scopes usually end in `.write`; Registrar's is `registrar-domains.admin`, and `registrar-domains.write` does not exist. Verify every id against `OAuthScopeCatalog.json` — `sanitized()` drops unknowns silently. Workers permissions remain fine-grained.
- Lists should stay lazy or use `List`; avoid loading unbounded object/key collections into a non-virtualized stack.

## Cloudflare API package

- Keep `packages/cloudflare-api` dependency-free and Foundation-based.
- New endpoints go through `CloudflareClient` so they inherit Bearer auth, single-flight refresh, and one retry after 401.
- Public response types are `Codable` and `Sendable`; public operations use `async throws`.
- Binary endpoints use `Data` or file URLs. Do not decode unbounded bodies as text unless the endpoint is known to be bounded.

## Edge app (landing + OAuth + registration)

Cloudflare accepts only HTTP(S) redirect URIs. The registered HTTPS callback is
served by worker `dash-relay` at `https://dash.xat.sh` (`apps/web`): a Vite React
landing SPA plus a Hono Worker that redirects OAuth to `dash://oauth/callback`.

Route ownership:

- `GET /` and SPA navigations → Workers Assets (landing)
- `GET /health` → liveness probe
- `GET /oauth/callback` → 302 to `dash://oauth/callback` (worker-first)
- `GET /api/registration/:domain` → RDAP then port-43 WHOIS snapshot for the
  iOS zone registration card (Cache API only; worker-first)

**There is no push bridge, and Dash sends no notifications of its own.** The
relay used to carry `/push/*`: an APNs client, an HMAC notify capability, a
silent-push possession challenge, a per-device Cloudflare webhook, an alert
mapper, and a `DashNotificationService` extension to localize what it forwarded.
All of it is gone, together with `aps-environment`, the time-sensitive
entitlement, the `remote-notification` background mode, `notifications.write`,
the notification-policy screen, and the per-domain alert subscriptions on zone
settings. Removing it also removed the only way the relay could fail a sign-in:
registration is what returned 502 when APNs was unreachable.

What is left is what was already true of builds: the Workers and Pages build
**Live Activities poll** while a screen or an activity is consuming them
(`Activity.request(…, pushType: nil)`, the shared
`BuildMonitorRefreshDisposition` backoff, a three-minute `staleDate`), so they
need no APNs token, no push-to-start, and nothing for an edge worker to forward.
A Live Activity is raised two ways and only two: the deployment screen's initial
refresh finds a build already running (the only way to catch one started on the
web), or `retry()` hands the returned deployment straight to
`PagesBuildActivityController.adopt` so a build started *in* Dash does not wait

Watchtower still reads Cloudflare's own delivery history over the API
(`listNotificationHistory`, `notifications.read`), which needs no infrastructure
at all. Do not reintroduce a delivery path to make that inbox "live", and do not
add a scope for an endpoint no screen calls. Where an alert *also* went — email,
a webhook — is configured in the Cloudflare dashboard, not in Dash.

Invariants that still hold:

- Zero storage (no KV, DO, or D1) and no secrets: `Env` is empty. Everything the
  worker still serves is either static or unauthenticated.
- Never touches Cloudflare credentials, OAuth tokens, or the PKCE verifier.
- Never logs request URLs (`invocation_logs: false`). The reason changed but the
  rule did not: `/oauth/callback` carries the Cloudflare authorization code in
  its query string.
